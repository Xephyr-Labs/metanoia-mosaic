# Personalization and data

The SQLite store persists users, host profile seed data, edited preferences, conversations, completed and interrupted messages, manually saved memories, usage records, and uploaded images. Data is scoped by chatbot instance and resolved user. Conversation deletion removes its messages, uploaded images, and derived-memory rows; full user-data deletion also removes preferences, memories, and usage.

The assistant context combines configured personality, host profile values, user-edited preferences, a bounded conversation summary with its own reserved budget, bounded recent completed messages, and a bounded lexical selection of saved memories. The stable assistant instructions are sent as a separate first system message so changing per-user data does not change the cacheable prefix. Personalization data is bounded by `context.personalizationTokens` (default: at most 800 tokens and 20% of the input budget); current-turn text and fixed instructions keep priority. Setting personalizationTokens to zero disables profile and memory injection while retaining the conversation summary. Memories are selected by simple lexical overlap, not semantic/vector search, and memories unrelated to the current message are omitted. The context builder uses a conservative text estimate and supports an image token reserve. Provider-reported usage and estimates are stored separately. Summary and memory-maintenance calls are recorded as separate usage types. A full user-data deletion aborts and waits for that chatbot instance's active replies before removing its records. With PostgreSQL shared across multiple Node.js processes, the host should quiesce that user's traffic on every process during deletion; cross-process in-flight request fencing is not implemented yet.

For personalization from the integrating application, resolve the authenticated session on the server and return a stable `userId` plus a small, relevant `profile` object. That profile is refreshed on requests and injected as untrusted factual context; never accept it from browser request JSON. Do not dump full account, billing, support, or activity records into the prompt. Registered host tools let the model request specific live data; callbacks receive the authenticated identity and request. Each callback must enforce its own resource-level authorization. Semantic memory search and built-in web search are not included.

Users add and edit memories manually by default. Set `personalization.autoMemory: true` to ask the configured provider to extract a few bounded, durable facts after a configurable number of messages. This makes an additional provider request and uses tokens. The chatbot filters likely credentials and sensitive topics, and users can inspect or remove saved facts. Summary creation runs after `context.summaryAfterMessages` is exceeded; failures preserve recent history and emit a maintenance event. Summary batches include complete messages in chronological order and advance the summary cursor only over those messages. Oversized messages are processed in bounded sequential chunks; the cursor advances only after every chunk succeeds. Maintenance runs after the reply lock is released, with a separate maintenance lock; subsequent turns can proceed while it runs. SQLite is intended for one process. Use PostgreSQL for shared state. Back up the SQLite file or PostgreSQL database and connect account deletion to the user-data endpoint.

Memories are included as context, never as system instructions. Avoid saving credentials or highly sensitive personal data. The application owns its data retention and backup policies.
